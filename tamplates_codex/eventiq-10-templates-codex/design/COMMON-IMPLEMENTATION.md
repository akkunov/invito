# Общие требования реализации Eventiq — 10 шаблонов

## Приоритет мобильной ширины (обязательное уточнение к предыдущим ТЗ)

Не делать узкий телефон внутри телефона. Публичное приглашение занимает всю доступную ширину при 320–430 CSS px; внешние отступы 0, width:100%, min-width:0, box-sizing:border-box. Внутренние отступы определяет композиция, обычно 20–28 px; фото обложки могут идти edge-to-edge. Проверить 430 × 932 как основной новый viewport, дополнительно 320×568, 360×800, 375×812, 390×844, 412×915. У ранее утверждённых макетов 390 px сохранять исходные размеры в их geometry.json, но адаптировать размещение на 430 px. Не задавать iframe/артборду fixed width 390 на 430-экран, не применять transform:scale к живым формам, не тянуть фотографии или весь растр. Desktop и существующий editor chrome не менять. В широком каталожном превью допустима ограниченная ширина существующего компонента; это не должно ограничивать мобильную публичную страницу. Высота артборда — целевая для эталона, не viewport и не фиксированная высота всей страницы. Длинный текст/локализация/ошибки расширяют секцию.

## Архитектура

Сначала прочитать актуальные DESIGN.md, UX-CONTRACT.md, Studio v2 schema, personalization, renderer, media, publication, RSVP, OpenAPI и import scripts. Все шаблоны — независимые versioned Template Package v1. Не импортировать blueprint из handoff: это проект контракта, не проверенный пакет. Не дублировать редактор UniversalMobileEditor. Общие виджеты должны быть опциональными параметрами и проходить строгую Zod-валидацию на frontend/backend. Без ветвления бизнес-логики по slug. Не менять существующие версии, черновики, опубликованные снапшоты, дизайн каталога. Если блок уже добавлен параллельным Codex, переиспользовать, не создавать второй. Обновить exhaustive switches, валидаторы ссылок, хэш, fork, personalization, asset collection, import allowlist, OpenAPI, редактор, публикацию и тесты при добавлении новых типов. Locked/aria-hidden декоративные SVG/маски, независимые редактируемые фото и текст; не использовать полный растр интерфейса фоном. Фото HEIC/HEIF/JPEG/PNG/WebP через существующий prepareCustomerPhoto, никаких требований к исходному разрешению для гостя. Не отключать строгую проверку WebP/PNG; для SVG использовать канонический LF и общий валидатор.

## Контролы (для всех новых вариантов, если индивидуальная спецификация не уточняет)

CSS px: input min-height 48, font 16/22 normal, border 1, horizontal padding 14; label 15/20 weight 600, gap 8; placeholder muted, label не заменять placeholder. Textarea min-height 88, padding 14, auto-grow, max 500 символов, счётчик 13/18; radio rows min-height 48, circle 20–22, gap 10, выбранный вариант виден по значку и цвету. Две колонки только если помещаются без обрезки, иначе stack. Stepper: высота ≥48, кнопки −/+ ≥44×44, number 18/24 tabular, предел 1..maxGuests; attendance=no → guests=0 и скрыть stepper. Primary CTA min-height 52, padding 14×18, font 16/22 weight 600; secondary map/calendar min-height 48. Select при старом варианте min-height 48, native popup. Music: min-height 72, фото 52×52, кнопка ≥44, реальное состояние playback. Иконки Lucide или существующие SVG 20–24px, доступные названия. Focus-visible outline 2px + offset 3px, контраст AA, на тёмном фоне контрастный светлый outline; active без смещения layout; disabled не кликается; pending удерживает размеры и блокирует повтор; inline error с aria-invalid/aria-describedby, сохранять данные и фокус первого ошибочного поля; success только после подтверждённого API, preview явно без отправки. Закрытый RSVP — объяснение без активного submit. Reduced motion: без обязательной анимации, весь контент доступен клавиатурой/скринридером.

## Данные и API

RU/KY, прямые шрифты с Ө Ү Ң, без курсива (даже если он есть в генерации). Даты: единый ceremonyDate ISO offset, отображение Asia/Bishkek; 29.05.2027 17:00 +06:00 — демо, не текущая дата пользователя. Календарная сетка/ICS/билет используют ту же дату. ICS корректно экранирует строки, UTC DTSTART, stable UID, CRLF, line folding, при отсутствии реального конца не выдумывать. Демо адреса, имена и фото заменить в редакторе, не выдавать за реальные заведения. Музыка из действующего лицензированного каталога, не использовать имя исполнителя на макете как обещание доступности. Видео только при проверенном медиа и наличии прав, не рисовать фальшивую кнопку play. Никаких запросов к непроверенным внешним URL. RSVP wish (nullable, ≤500) — переиспользовать миграцию Italian Romance если есть; иначе добавить один раз через frontend+API+PostgreSQL+owner dashboard и идемпотентность (повторный requestId не изменяет сохранённый ответ). Turnstile, throttle, ownership, дедлайн, лимиты гостей сохраняются. Пожелания приватны владельцу, не возвращать публично.

## Проверка и merge

Для каждого шаблона: typecheck frontend/backend, build, npm run test:<slug>, регрессии всех шаблонов, тест загрузки фото, PostgreSQL E2E на отдельной БД: импорт, защита от дубликатов, редактирование, сохранение, публикация, RSVP, wish, смена локали, новые поля. Playwright Chromium + WebKit по возможности: скриншот каждого артборда (DPR 1), сравнение с соответствующим референсом, проверить длинные имена, пустые/частичные фото, загрузку HEIC, ошибку сети, keyboard, reduced motion, отсутствие horizontal overflow, видимость и размеры всех контролов. Визуальная цель — близкая композиция, а не растянутый растр; отклонение основных статичных элементов до 4 CSS px там, где пропорции совпадают, динамический контент может расширяться. Зафиксировать actual differences, команды и результаты в docs/studio-v2/<NAME>.md. Отдельные ветки feat/<slug>-template только после согласованного общего контракта; не force push, не перетирать параллельные изменения. Перед merge актуальный main и повтор тестов. Не трогать production DB.
