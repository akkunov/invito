# Eventiq — инструкции для задач Codex

## Старт задачи

- Проверь актуальный `origin/main`, статус рабочей копии и ветку заданного этапа. Открой [статус проекта](docs/architecture/PROJECT-STATUS.md), [план 4.1](docs/architecture/EVENTIQ-4.1-MASTER-PLAN.md), карточку задачи и связанные [решения](docs/architecture/DECISIONS.md).
- Фиксируй базовый SHA. Сверяй прошлые отчёты с кодом, миграциями и результатами проверок. Отдельно отмечай, что присутствует в Git, что проверено на тестовом стенде и что выпущено в рабочую среду.
- Работай по одному ID с проверяемым результатом. Сохраняй контекст в карточке задачи и реестре статуса. При ошибке записывай условие воспроизведения, фактический результат и следующее действие.

## Архитектура и стек

- Frontend — Next.js App Router, React, TypeScript, Zod, CSS, Supabase SSR. Маршруты и серверная композиция в `src/app`, клиентский UI в `src/components`, доменные модули в `src/features`. Используй точные версии из lockfile. Перед изменением API Next.js проверь документацию установленной версии в `node_modules/next/dist/docs`, если она доступна.
- Backend — NestJS, TypeScript, Zod, Prisma и PostgreSQL. HTTP-контракты и OpenAPI, доменные операции и база разделены. Supabase выдаёт сессии и токены. Cloudflare R2 хранит проверенные медиа. Смотри [карту проекта](docs/architecture/EVENTIQ-4.1-MASTER-PLAN.md#карта-проекта).
- Общие контракты Studio v2 живут в `src/features/studio-v2/core`; ядро остаётся независимым от React, Next, браузера и Prisma. Общий рендер использует `StudioV2ProjectRenderer`, клиентский редактор — `UniversalMobileEditor` и разрешения `PersonalizationContract`. Сохраняй рабочие legacy-адаптеры до проверки совместимости. Пакеты и исходные артборды хранятся отдельно. [Studio v2](docs/studio-v2/ARCHITECTURE.md) · [Коллекция](docs/studio-v2/TEMPLATE-COLLECTION.md)
- Nest-контроллеры валидируют вход и передают запрос сервису. Правила владения и атомарные изменения принадлежат доменной операции. Next получает данные через существующие контракты, приватные состояния ограничивает пользователем и очищает при смене сессии. Не кешируй приватные данные в общем кеше.

## Код и данные

- DRY и SOLID применяй там, где операции действительно разделяют контракт и ответственность. Предпочитай простые, читаемые решения (KISS). Добавляй абстракцию, зависимость или инфраструктурный компонент только при доказанной потребности. Используй существующий путь исполнения, без параллельного рендерера, редактора, пайплайна загрузки или веток по slug для общих возможностей.
- Держи TypeScript строгим. Для внешних данных используй `unknown` и проверку общей Zod-схемой. Дополняй контракты обратно совместимо, валидируй связанные значения, явно обрабатывай варианты discriminated union и ошибки. Не обходи валидацию через `any`, двойное приведение, `@ts-ignore` или дублирующую упрощённую схему.
- Проверяй идентификацию, права области и владение на сервере. Ограничивай вход, частоту запросов и размер медиа; проверяй MIME, байты и права доступа. Храни секреты на сервере. Не записывай токены, подписанные URL, номера, имена гостей и содержимое сообщений в логи. Сетевые интеграции используют проверяемые адреса, таймауты и ограниченные повторы. [Persistence](docs/backend/ADR-029-01-PERSISTENCE.md) · [Медиа](docs/backend/ADR-029-04-MEDIA.md) · [Публикации и RSVP](docs/backend/ADR-029-05-PUBLISHING.md)
- Prisma-миграции добавляй по возможности аддитивно. Используй отдельный disposable PostgreSQL для проверки нового запуска и перехода с предыдущего релиза. Переигрываемые backfill и операции записи проверяй на повторы, конкуренцию и частичные сбои. Записи в production, миграции, смена публичных указателей и удаление данных требуют явного разрешения. Не применяй `db push`, reset или ручную чистку в production.
- Сохраняй ID, slug, права, старые форматы пакетов, черновики, опубликованные URL, снапшоты и хеши. Дизайн уже импортированного шаблона обновляй добавлением версии к существующему ID с CAS и явной публикацией. При несовпадении identity либо неоднозначном совпадении останови операцию без записи. [Пакеты](docs/backend/TEMPLATE-PACKAGE-V1.md) · [Версии каталога](docs/backend/SERVER-TEMPLATE-CATALOG.md)

## UI, UX и визуальная проверка

- Переиспользуй контролы и семантику из [DESIGN.md](DESIGN.md) и [UX-CONTRACT.md](UX-CONTRACT.md). Проверяй RU/KY, форматы даты и шрифты, клавиатуру, фокус, touch, safe area, reduced motion, пустые, медленные и ошибочные состояния. Продуктовый chrome и авторский артборд имеют отдельные правила оформления.
- Сверяй шаблон с оригиналом из `tamplates_codex/eventiq-10-templates-codex`. Для выявленного ограничения расширяй общий движок с обратной совместимостью. Для каждого артборда приложи оригинал, реальный рендер и diff при одинаковых размерах и DPR. Фиксируй браузер, шрифты, локаль, состояние и версии. [Протокол 4.1](docs/architecture/EVENTIQ-4.1-MASTER-PLAN.md#протокол-visual-fidelity)
- Ручная визуальная приёмка и автоматическая функциональная проверка учитываются отдельно. Любой допуск по композиции, фото, типографике или поведению должен быть зафиксирован и согласован. Отсутствующий артефакт или стенд отражай в статусе и не выдавай повторную приёмку за пройденную.

## Git и Definition of Done

- Используй отдельную ветку от актуального `origin/main`, небольшие коммиты и PR. Сохраняй чужие изменения. Не используй force push. Сливай или разворачивай только при наличии поручения и прохождении относящихся к изменению проверок.
- Для изменений поведения выполняй затронутые typecheck, lint, production build и регрессии, а для данных также миграции и PostgreSQL E2E. Для UI используй Browser/Playwright и требуемые размеры экрана. Для документации проверяй ссылки, покрытие требований, таблицу статусов, граф и область diff. В PR разделяй фактические результаты, исходный baseline и пропущенные проверки с причинами. [Studio quality gates](docs/studio-v2/QUALITY-GATES.md)
- Перед `DONE` проверь acceptance criteria, сохранность данных и обратную совместимость. Запиши ветку, SHA, PR, воспроизводимые тесты, ручную приёмку, ограничения и откат. Зафиксируй отдельное подтверждение там, где требуется визуальная или внешняя приёмка. [Как вести статус](docs/architecture/PROJECT-STATUS.md)
