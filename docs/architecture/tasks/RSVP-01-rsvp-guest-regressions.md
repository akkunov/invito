# RSVP-01 — Надёжность гостевой формы и исторических релизов

Приоритет `P0`. [Реестр задач](../PROJECT-STATUS.md)

## Цель

Зафиксировать совместимость двух путей RSVP перед добавлением уведомлений.

## Текущее состояние

Есть customer и Studio flows, проверка активного релиза, хеша, guest limits, requestId, Turnstile, wishes для разрешённых пакетов.

## Зависимости

[000](000-eventiq-4-1-foundation.md)

## Scope

Матрица yes/no, пожеланий, лимитов, дедлайна, повторов, ошибок и приватного списка. Исправлять только подтверждённые сбои.

## Non-goals

Объединение таблиц RSVP, отправка WhatsApp, перезапись guest snapshot.

## Архитектурные требования

Сохранять две модели и защиту публичного входа, preview не вызывает live transport, формы доступны RU/KY.

## План реализации

Собрать fixture двух поколений; проверить race с unpublish/republish; зафиксировать ошибку на каждом состоянии; сохранить ответы при сбоях.

## Acceptance Criteria

Старые релизы читаются; повтор requestId не удваивает запись; UI показывает корректный успех/отказ и без транспорта в preview.

## Обязательные тесты

Backend e2e/contract, Playwright обе локали с touch и keyboard, timeout/retry, unpublish/release race.

## Миграции

Нет без конкретного подтверждённого дефекта.

## Rollback Plan

Откатить только исправление поведения; гостевые записи остаются.

## Definition of Done

Acceptance Criteria закрыты воспроизводимыми проверками. В реестре указаны SHA, PR, проверенная среда, результаты, ручная приёмка или основание «не применимо» и ограничения. Откат проверен в объёме задачи.
