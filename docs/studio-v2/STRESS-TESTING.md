# Studio v2 #28.9.3 — Maximum-document stress testing

## Fixture and isolation

Generated by `scripts/studio-v2-stress-fixture.mjs`: **30 pages, 500 live nodes (including 30 root frames), 200 assets**. Each page contains 15–16 editable children. The fixture uses a separate `studio-v2-stress` project ID and a fresh Playwright browser context. PNG blobs are generated in the browser and written to IndexedDB before Studio opens; the test never overwrites a real user's project or uses production API endpoints.

## Measurements

- **Core** (Node.js 22): schema validation, layout resolution, viewport window selection, and one edit + undo/redo; each produces sample count, p50, p95 and maximum milliseconds.
- **Chromium** (1600 × 1000): cold local project load + initial autosave, mounted vs retained page shells, navigation across widely separated artboards, frame pacing during wheel panning, DOM node count, JS heap, loading all 200 local PNG assets, editor property changes, undo/redo, and reload persistence.
- **Narrow UI** (390 × 844): real responsive panels, far-page navigation and screenshot.

Both tests write structured JSON under `studio-browser-artifacts/`, including `stress-core.json` and `stress-browser.json`. Chromium also writes desktop/mobile evidence images. Both PR and deployed GitHub Pages workflows run the same stress workload; artifacts are downloadable from Actions.

## Interpretation and gates

Functional invariants (valid fixture, 30 shells, offscreen artwork not mounted, selected artboards visible, 200 decoded asset previews, correct editing/history/persistence, no runtime errors) are hard gates. Navigation p95 above **15 seconds** is an explicit failure indicating serious regression, not an acceptable UX target. Frame intervals and JS heap are recorded as observations; thresholds must be set only after a stable baseline with repeated runs on identical hardware. Do not compare absolute p95 across unlike CI runners or assume a single run proves 60 FPS. Some Chromium memory counters may be unavailable and are recorded as null, not fabricated.

The stage currently holds full document validation and layout work on the main thread; this phase establishes numbers and diagnoses bottlenecks rather than promising stable FPS or a specific heap cap. Subsequent optimizations must keep the same fixture and track p95 against a pinned baseline. Public/print renderers still render all content, preserving export completeness. Browser stress uses generated 16 px images, not 200 real photographs; large photo decompression needs a separate media-weighted benchmark.

## Runbook
